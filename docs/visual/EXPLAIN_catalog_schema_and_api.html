MiaMedical · planning artifact

Catalog domain — final schema & API shapes

The data model and wire format proposed in the implementation plan, before any code is written. Italian-first bilingual catalog, fixed-or-rental pricing, per-product variants, category-owned specifications, R2 media. Review this alongside the plan — nothing here is built yet.

Entity table Translation table — indexed text, one row per language Join / matrix table Content

The i18n rule, in one line: if PostgreSQL has to search or index the text, it gets a translation table. Everything else gets an inline { "it": …, "en": … } jsonb column.

That leaves exactly three translation tables — products and categories (full-text search and a per-locale slug) and terms documents (per-locale slug). The other eleven translatable entities carry their labels inline, because nobody ever searches a variant option's label, and a table for it would cost a second write and a second query on every read. In the diagram below, IT·EN marks a translation table and json marks an inline column.

Money is numeric(12, 2) — exact decimal, two places — and travels as a string. Not integer cents. Three things follow from that, and all three are load-bearing:

1. Drizzle maps numeric to a JavaScript string by default. mode: 'number' exists and we deliberately do not use it — going through a JS number is what loses precision. 2. That string is also what keeps the two decimals alive through JSON: a JSON number 10.00 serializes back as 10, whereas "10.00" survives intact. 3. Arithmetic never touches floats. 35.00 + 4.00 + 16.5 × 0.25 in IEEE-754 gives 43.129999999999995. A small money.ts does the sums in bigint hundredths with half-up rounding and formats back, so the answer is "43.13".

PostgreSQL numeric is not a float, so the schema's old warning — "never store money as a float" — still holds. It is narrowed, not broken.

1 · How the pieces fit

Three entities are a pair — a base table plus a *_translations table keyed (entity_id, language_code). The rest keep their text on the row itself. The chip on each box says which.

Read the dashed arrow as a "copy", not a foreign key. Toggling an attribute preset onto a product duplicates it into product_variant_groups. After that the product owns its variants outright — editing the preset later never touches an existing product. Only source_preset_key records where it came from.

2 · Tables in full

21 tables: 18 entity tables (3 of them joins) and 3 translation tables. Columns typed localized are inline { it, en } jsonb, each carrying a CHECK (col ? 'it') so Italian is mandatory in the database — something a translation table cannot express without a trigger. Columns named icon are a nullable text holding one R2 object key — always a square WebP, sized by the profile table in Icons below. Every column follows the existing house conventions — uuid primary keys with defaultRandom(), camelCase in TypeScript mapped to snake_case by Drizzle's casing option, and timestamp({ withTimezone: true }) throughout. Timestamps are omitted below for brevity; every base table carries created_at, and mutable ones also updated_at.

An addon's pricing mode is bounded by its product's. Renting something out means you get it back; selling it means you do not. So a rental addon on a sold product is meaningless — nothing is returned and there is no period to bill against.

Product modeAllowed addon modesExample
rental rental and fixed mattress at €9,00/day (comes back) + delivery at €60,00 (does not)
fixed fixed only cushion sold alongside the wheelchair

A plain CHECK cannot see the parent row, so product_addons carries a denormalised product_pricing_mode. That is normally a sync hazard — here it cannot drift, because products.pricing_mode is write-once and never updated. To make the copy provably correct rather than merely trusted, products gains UNIQUE (id, pricing_mode) and the addon's foreign key becomes composite: 

ALTER TABLE product_addons
  ADD CONSTRAINT product_addons_product_fk
  FOREIGN KEY (product_id, product_pricing_mode)
  REFERENCES products (id, pricing_mode) ON DELETE CASCADE;

ALTER TABLE product_addons
  ADD CONSTRAINT product_addons_mode_check
  CHECK (product_pricing_mode = 'rental' OR pricing_mode = 'fixed');

PostgreSQL then guarantees the denormalised value matches its parent. No trigger, no application invariant anyone has to remember.

Media — no tables at all, and three fields per item

Product media is never searched, never filtered, and never shared between products, so a normalized media library was buying referential integrity we do not need at the cost of four tables and a join on every read. It collapses into one jsonb column on products, typed at the Drizzle boundary exactly the way products.metadata already is in the current schema. 

// packages/db/src/schema/media-types.ts
type MediaAlt = Partial<Record<LanguageCode, string>>;

interface MediaItem {
  path: string;      // R2 object key — never a URL
  mimeType: string;
  alt?: MediaAlt;     // also the visible label for a PDF
}

interface ProductMedia {
  thumbnail: MediaItem | null;
  cleanPng:  MediaItem | null;
  gallery:   MediaItem[];
  videos:    MediaItem[];
  documents: MediaItem[];          // the PDFs
}

// in products:
media: jsonb().$type<ProductMedia>().notNull().default(EMPTY_PRODUCT_MEDIA),

// on categories, category_specs, product_variant_groups,
// attribute_presets, product_addons — the R2 key, nothing else:
icon:  text(),                       // nullable

title, width, height, sizeBytes and durationSeconds are all gone. Two consequences worth stating up front rather than discovering later: a PDF's label is now its alt ({ it: "Scheda tecnica", en: "Datasheet" } becomes the link text), and without intrinsic dimensions the storefront reserves space in CSS rather than in HTML. For icons that costs nothing — every icon is a known square, so its dimensions are compile-time constants. For gallery images it means an aspect-ratio box. Fixing sizes at upload is what makes that safe.

Icons — five entities, two sizes, one text column

An icon is not a MediaItem. Both of that type's other fields would be dead weight here: mimeType is always image/webp by construction, and an icon sits next to the label it decorates, so its accessible name is that label — an alt would be a duplicate to keep in sync across two languages. A plain text column also makes WHERE icon IS NULL an ordinary index-friendly predicate rather than a jsonb probe, which is exactly the query behind the admin's "categories still missing an icon" view.

TableProfileStored as
categoriesicon_256square, exactly 256 × 256 WebP
category_specsicon_256square, exactly 256 × 256 WebP
product_variant_groupsicon_256square, exactly 256 × 256 WebP
attribute_presetsicon_256square, exactly 256 × 256 WebP
product_addonsicon_1024square, up to 1024 × 1024 WebP

attribute_presets is on the list for a reason that is easy to miss: a preset is copied into a product as a variant group. If the group carries an icon and the preset does not, every group seeded from the library starts iconless and someone re-uploads the same ruler icon per product. product_variant_options deliberately does not get one — colour swatches are the same one-line column, but an icon per option means an upload per option and a much heavier variant editor.

Every image is WebP; video is only bounded

Whatever is dropped in — JPEG, PNG, HEIC, AVIF — is converted to image/webp in the browser before upload, and the presigned URL is signed for image/webp, so nothing else can be stored. cleanPng keeps its key name for continuity but its content is WebP too: WebP carries an alpha channel, so the transparent cutout survives intact. Video is not converted, only limited. Enforcement is three layers deep, because each one alone has a hole:

LayerWhereCatches
Convert & cropbrowser, OffscreenCanvas.convertToBlobthe normal case — a 6 MB HEIC becomes a ~40 KB 256² WebP
Signed ContentTypeR2 rejects the PUT itselfa client that skips conversion and PUTs a JPEG
probeImage()server, on save — ranged GET of 64 bytes, parses the RIFF/WebP headera genuine but oversized or non-square WebP

That third layer is what turns "no matter what size they upload it is 256 px" into a guarantee rather than a convention. It is roughly 30 lines, needs no new dependency, and never transfers the file body — VP8, VP8L and VP8X all carry width and height in the first 64 bytes.

ProfileMimeMax bytesGeometry
product_imageimage/webp5 MBany ratio, longest edge ≤ 2048
icon_256image/webp256 KBsquare, exactly 256
icon_1024image/webp1 MBsquare, ≤ 1024
videovideo/mp4 · video/webm50 MBunconverted
documentapplication/pdf20 MB—

The table lives in packages/validators/src/media.ts and is imported by the presign route, the admin uploader and the save path, so the three can never disagree. It is code rather than env config on purpose: these limits are contract, not deployment tuning.

This is not a contradiction of the translation-table decision. Every other translated field was just moved out of JSONB — and here alt goes back into it. That is deliberate. The case for translation tables rested on per-language tsvector indexes, granular updates and join efficiency. Alt text is never searched, never filtered, never queried on its own, and is only ever written as part of a whole-product save. None of the three reasons apply.

The real cost is orphaned objects, and it needs handling. With no media_assets row there is no inventory of the bucket, so nothing notices when an image is dropped from the array. Two mitigations, both in modules/products/media/service.ts:

On save — diff the incoming media against the stored one and call storage.delete(path) for every path that disappeared. This is the main line of defence and needs no table. On abandon — an upload that is presigned but never saved leaves a stray object, so presigned keys are minted under products/_staging/<uuid>/ and moved to products/<id>/ on save. A scheduled sweep can then delete anything left under _staging/. That sweep is out of scope here — the prefix convention exists from day one so it is not a painful retrofit.

And money arrives as a decimal string, so render it with formatMoney() in each app's lib/api.ts — whose signature changes from cents to that string. Neither is an oversight; both keep the CDN domain and the display locale out of the database.

pricingModeLocked is why the field can be shown but not edited. It is always true on an existing product — the create endpoint accepts pricingMode, the update schema omits it entirely, and the repo's UPDATE never names the column. 5 · How a price is resolved

Both modes store the price in the same column — products.base_price. There is no separate fixed-price column and no separate rental-price column; pricing_mode is what tells you how to read the number, and rental_unit is NULL exactly when the mode is fixed. 

  Carrozzina                        Letto
    pricing_mode = 'fixed'            pricing_mode = 'rental'
    base_price   = 450.00             base_price   = 35.00
    rental_unit  = NULL               rental_unit  = 'day'

    → €450,00 once                    → €35,00 per day

Two columns would mean one is always NULL, plus a constraint to ensure the right one is filled for the mode. Since a product is one thing or the other and cannot change, a single column carries no ambiguity. The same shape applies to product_addons.price.

From there, one function in modules/products/pricing.ts produces every money value on both surfaces. Worked through with the rental product above, configured as grigio · con sponde · materasso 16,5 cm:

StepSourceAmountRunning total
Base priceproducts.base_price35.0035.00 / day
Colore → Grigioproduct_variant_options.price_modifier+ 4.0039.00 / day
Sponde → sìproduct_variant_options.price_modifier+ 6.0045.00 / day
Altezza materasso 16.5 cm16.5 × price_modifier_per_unit (0.25)+ 4.125 → 4.1349.13 / day
Note consegna (free text)no price effect—49.13 / day
SKU overrideproduct_skus.price_overrideif set, replaces everything above

Because pricing_mode is rental with rental_unit = 'day', every one of those modifiers is per day — that is precisely the rule that lets the modifier column stay a bare number with no unit of its own. On a fixed product the identical arithmetic yields a one-off amount. Addons never enter this calculation: each prices against its own mode and unit — which for a fixed product is always fixed, and for a rental product may be either — and the order total sums the two.

Row four is the whole reason money is not a JS number. 16.5 × 0.25 is 4.125, which must round half-up to 4.13. Computed in IEEE-754 the running total comes out 49.129999999999995; computed in bigint hundredths it is exactly "49.13". Whenever the price is needed inside a query — sorting, or a price BETWEEN filter — the same arithmetic is expressed in SQL instead, where numeric is already exact.

SKU composition

Only groups with affects_sku = true take part — here colore and sponde. The numeric and free-text groups do not, which is what keeps the matrix finite. 

  MIA-LTE      -    GRI  CS    -   P3XT
  ───────           ───────        ────
  products          sku_code of    stable random tail,
  .base_sku         each chosen    minted once and never
                    option         recomputed

The tail adds no uniqueness — UNIQUE (product_id, combo_key) and a unique base_sku already guarantee that. It exists so the SKU survives an option being renamed: the composed middle would change, but the stored sku and suffix keep the row's identity fixed for every label, quote and past order that already references it.
