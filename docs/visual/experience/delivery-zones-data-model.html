Delivery pricing · data model

The same rows, shown three ways

Two tables. One is a flat dictionary of Italy, imported once. The other is your client's price list, and it is a tree made from a single column — parent_id.

1The two tables, as Postgres holds them

Note what is not in the first one: no parent, no nesting. Every comune carries its province and region as plain columns, which is all you need to know where an address is.

istat_comuni flat · imported · read-only 7,900 rows
istat_code name province region
istat_comune_caps which CAPs each comune contains ~10,000 rows
istat_code cap note

2delivery_zones — the price list, and the tree

One row per priced area. parent_id is the only thing making it a tree — everything else is ordinary columns. A null in value_kind means "inherit from above"; call means "we serve it, quote by phone".

delivery_zones flat, as stored ~200 rows in practice
id parent_id level code name value_kind fee
the same rows, following parent_id nothing else stored

Look at z7 and z10: both have code = '00060'. Same CAP, different parent_id, so they are different areas at different prices — which is legal because the unique index is on (parent_id, level, code), not on code alone.
