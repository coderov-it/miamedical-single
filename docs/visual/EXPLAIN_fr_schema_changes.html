Schema impact of adding fr

The translation tables are keyed (parentId, languageCode) and the inline columns are jsonb. Both store a language as a row or a key, never as a column — so a third language is one ALTER TYPE and no table ever changes shape.

Two things to verify before the migration

The french text-search config must exist on the instance. It ships with a default PostgreSQL build, but a slim image can omit it, and searchVectorFor() would then throw on every French insert.
SELECT cfgname FROM pg_ts_config WHERE cfgname = 'french';
ADD VALUE must commit before anything uses 'fr'. PostgreSQL will not let a transaction insert a value it added itself, so this cannot be bundled with a seed or a data migration — keep 0011 alone and let 0012 use it.
SELECT unnest(enum_range(NULL::language_code)); -- expect it, en, fr
blog_post_translations has no search_vector. Blog search does not exist in any language today — French does not regress it, but if the fr launch is meant to include blog search, that column and its GIN index are a separate migration.
