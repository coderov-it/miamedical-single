A fact writes a notifications row inside the transaction that caused it, and the same transaction calls pg_notify. At COMMIT the hub wakes, finds the recipient's open SSE streams, and pushes the row. If the transaction rolls back, the row and the notice vanish together. That pipeline is done and it is audience-agnostic — it already writes audience='customer' rows today.

Settled in review. iOS will not accept a push that did not come from Apple's APNs, and Android's is FCM — but Firebase relays to APNs for free once an Apple .p8 key is uploaded to it. So one transport covers both platforms and we write one code path.

Your instinct that this is the lightweight option is right, and it is worth saying why: it is one POST to https://fcm.googleapis.com/v1/projects/{id}/messages:send carrying an OAuth2 bearer minted from a service-account key. No SDK, no vendor holding customer identifiers, and roughly forty lines for the token minting. It lands as infra/push/ laid out exactly like infra/mail/ — a port, an fcm adapter, and a console adapter that prints the payload so the whole flow is testable before a Firebase project exists.

The alternatives considered and dropped: @capacitor-firebase/messaging (same transport, less native work, bigger binary — reopen if the app team wants it, it changes nothing server-side), OneSignal (fast, but customer identifiers leave our infrastructure), and calling APNs directly (two senders, two credential formats, two error vocabularies).

A push needs a token. The OS issues one at registration and changes it — on reinstall, on restore, whenever it likes. So the app posts it on every launch and the server upserts.

CREATE TABLE push_devices ( id uuid PRIMARY KEY DEFAULT gen_random_uuid(), customer_account_id uuid NOT NULL REFERENCES customer_accounts(id) ON DELETE CASCADE, token text NOT NULL UNIQUE, platform text NOT NULL, -- 'android' | 'ios' language text NOT NULL, -- the device locale; see §6 last_seen_at timestamptz NOT NULL DEFAULT now(), created_at timestamptz NOT NULL DEFAULT now() ); CREATE INDEX push_devices_customer_idx ON push_devices (customer_account_id);

token is unique across the whole table, not per customer, and that is the point: a shared or resold phone would otherwise sit on two accounts and receive both people's orders. The upsert is ON CONFLICT (token) DO UPDATE — the newest sign-in owns the device. Sign-out deletes the row, because a token left behind keeps delivering to a phone nobody is signed into.

Your call is right, and it is the only correct one: push needs a signed-in account. A device row points at a customer_account_id, and the only thing that proves which account a phone belongs to is a session. Binding a token to anything weaker — an order number, an email typed at checkout — would let anyone who learned an order number subscribe to that order's notifications. There is no version of this that safely reaches an anonymous device.

What is not true is that a guest loses anything. Every checkout already creates an account row, signed in or not — resolveForOrder finds or creates one by email and marks the link unverified. So the notifications are being written for guests right now. They are undelivered, not missing:

1 anna@example.com checks out — not signed in 2 resolveForOrder → creates customer_accounts row, link 'unverified' 3 order row carries customer_account_id ← she has an identity 4 5 an operator moves the order to 'paid' 6 notifications row written against her account ← recorded 7 push? no push_devices row for that account → nothing sent ← the only loss 8 9 Anna opens the activation link in her order email, signs in 10 the feed opens with step 6 and everything since, already there 11 app registers her device → every later event also reaches the lock screen

So the exception costs a guest their real-time notifications and none of their history. That reframes the work: the thing worth building is not a way to push at step 7, it is a better nudge at step 9.

Today activation is asked for by email and nowhere else, which is why so many accounts sit unactivated. An app that has just taken a guest checkout knows the order number and the email at that exact moment, with the customer still holding the phone — a far better moment to ask than an inbox visited hours later. Worth raising with your developer as its own small piece of work; it is what turns this exception from a permanent ceiling into a first-order problem.

    The rule that makes this work: loc_args are plain positional strings, so anything passed as an argument is printed verbatim and never translated. Arguments therefore carry order numbers, counts and proper nouns — never a status, never a formatted date. Which is the same rule the notification payload already follows, applied one layer out.

    That is why the key above is order_status_changed_paid_body rather than a generic key with the status as an argument.     What we need back from the app

  • Permission before registration. requestPermissions() then register() — Android 13+ made this a runtime prompt too, so it is no longer an iOS-only step.
  • The token on every launch, and again on the token-refresh callback. Never cached and assumed stable; the OS reissues them whenever it likes.
  • The app version in that same call. It is what decides whether this phone is sent a localization key or a rendered sentence, so a wrong or missing value shows somebody a raw order_status_changed_paid_body on their lock screen.
  • The device locale too, as a two-letter code. Only used for the server-rendered fallback — the OS handles the language whenever keys are in play.
  • The generated string resources committed to the app repo, regenerated whenever copy changes. We produce strings.xml and Localizable.strings from @mia/i18n; nobody hand-edits them.
  • The unregister call before sign-out clears the session, not after. An orphaned token keeps delivering to a phone nobody is signed into.
  • A tap handler that follows data.route and marks data.notificationId read.
