Live notifications for the customer area

An in-app feed at /area-clienti/ and in the back office, pushed over SSE and fanned out by pg_notify from inside the transaction that caused it. One new table, no queue, no vendor, no polling.

apps/server/src/modules/notifications/ exists today and sends email, nothing else. It is fire-and-forget on purpose: sendQuietly logs a failure and carries on, because the order is already a recorded fact and a provider outage must not turn a delivery problem into a lost order. That reasoning still holds. What it costs is stated in the module's own documentation, twice:

No send log. Whether a given customer was actually emailed is only answerable from application logs, not from the database. … New orders do not alert the operator.

So a customer who misses one email has no second place to look, and an operator watching the admin panel has no signal at all. The customer area is already a Svelte island with a live session and its own router — it is the obvious place for a feed. And a feed row, written in the same transaction as the fact it reports, is also the send log the email path never had.

You asked for four events: an upcoming order, an order status change, a rental about to end, and a rental renewed. Two of those are transactions that already run somewhere in apps/server. Two are facts about a date that no transaction will ever produce — they become true while the process sits idle. That split decides the shape of everything below: the first pair needs a hook, the second pair needs a clock.

Admin first, then the customer area

Decided, and it is a better call than the one this plan originally recommended. I argued for building both at once so the shared seam was opened only once. That reasoning ignored the stronger argument: the admin panel has roughly five users on a known network, and the customer area has ten thousand at peak. Shipping the pipeline to the small audience first means every unknown in it — the listener reconnecting, the sweep's dedupe key, a stream surviving a deploy — is discovered against five operators who can be asked what they saw, not against a Black Friday crowd.

It also front-loads the part with no capacity risk at all. Five concurrent admin streams need none of the tuning discussed later; by the time the customer half is built, the pipeline itself is already proven and the only open question is connection count.

Everything that produces a notification produces it inside the transaction that produced the fact. The row and the push are two more statements in a BEGIN that is already open. Email stays where it is — after the commit, best-effort, unchanged.

The two channels having different durability is the point, not an accident. The feed row cannot exist unless the order actually moved, because it shares the order's transaction and its rollback. The email can be lost without losing anything, because the row is now the record.

Traffic is one-way, server to browser. SSE rides the cookie you already have: EventSource with withCredentials reuses mia_customer_session through the same CORS allowlist the RPC client uses, and hono/csrf only guards non-GET, so nothing in app.ts changes. WebSocket cannot set headers either — the usual reason people reach for it — but it leaves the upgrade, the reconnect loop and the heartbeat for us to write. The browser ships all three for SSE.

Postgres holds a NOTIFY until the transaction commits and discards it on rollback. An in-process emitter has to be called after commit by hand, at every call site, and one call placed before await tx resolves pushes a status change that was rolled back. The database enforces for free what a convention would have to be trusted with. It also turns out to be what makes clustering free — see the capacity section.

The client's state comes from GET /api/customer/notifications. The stream only says something changed, look again, carrying the new row as a convenience. Nothing is ever reconstructed from the sequence of frames, which is what makes a dropped connection a non-event rather than a correctness problem.

A row stores type: 'order.status_changed' and data: { orderNumber, from, to }. It does not store “Il tuo ordine è stato spedito”. The storefront runs in four languages and a stored Italian string cannot be one of the other three — nor can a copy fix reach a row written last month. This is also the repo's own rule: the keys are wire format and stay English, the words are content and live in @mia/i18n.

“The rental ends in three days” comes from an hourly sweep, the same shape as media/sweep.ts. Idempotency is a dedupe_key with a unique index and ON CONFLICT DO NOTHING, so a restart, an overlapping tick and a second API process all converge on the same single row. No watermark, no advisory lock, no decision about which box runs the cron.

You raised both of these, and they are the right two to have raised — if either had gone the other way the design above would be wrong rather than merely arguable.

Postgres does not lock the database for a transaction

It uses MVCC. A writer takes a row-level lock on the rows it writes and a RowExclusiveLock on the table — and that table lock conflicts only with ALTER TABLE, VACUUM FULL and non-concurrent CREATE INDEX, never with another write. Four concurrent transactions:

t=0ms TX-A: BEGIN t=1ms TX-A: UPDATE orders SET status='paid' WHERE id=A → RowExclusiveLock on table orders ← does NOT conflict with other DML → exclusive lock on row A only t=2ms TX-B: BEGIN t=3ms TX-B: UPDATE orders SET status='paid' WHERE id=B → same table lock, different row → proceeds, zero wait t=4ms TX-C: SELECT * FROM orders WHERE id=A → MVCC: reads the last committed version → proceeds, zero wait, sees status='pending' t=5ms TX-D: UPDATE orders SET status='paid' WHERE id=A → row A is taken → waits for TX-A ← the only blocker t=6ms TX-A: COMMIT → TX-D wakes, re-evaluates

Writers block writers on the same row. They never block readers, and readers never block writers. What this plan adds to that window is one INSERT into a table nothing contends on — new rows cannot conflict — and pg_notify, which appends to a backend-local list. Together, well under a millisecond on a transaction already doing an UPDATE and an INSERT.

At COMMIT, a backend carrying a pending NOTIFY briefly takes NotifyQueueLock to write into the shared notify queue. It does serialize those commits. It is held for microseconds and starts being measurable somewhere around 5,000–10,000 NOTIFY per second. The numbers in the next section put us three orders of magnitude below that, which is why this is worth knowing about and not worth designing around.

The vendor question

honker.dev is a SQLite extension. It exists to give SQLite the NOTIFY/LISTEN semantics that Postgres has natively, so that a SQLite-backed app can keep its queue in the same file as its data. We are on Postgres. Adopting it would mean moving the database to SQLite in order to get back something we already have.

The real category you were reaching for is notification-infrastructure products — Novu, Knock, Courier. They earn their price on multi-channel orchestration: SMS and push and in-app and email against a per-user preference matrix, digests and batching, templates edited by people who do not deploy, deliverability analytics. For four event types on one product, that is more integration surface — a network hop inside the order path or a webhook to authenticate, plus a second source of truth for what we told a customer — than the entire feature proposed here.

What Postgres genuinely does not give us: retries, a dead-letter queue, and durable per-consumer offsets. The design sidesteps all three by making the table the truth and the push a hint. The day that stops being enough — “push it even though the API was down for an hour” — the answer is an outbox worker reading the same table, not a vendor.

Two numbers matter and they are independent: how many notifications per second the database carries, and how many idle connections the box holds open. The first is not close to a limit. The second is a tuning exercise, not an architecture one.

Taking roughly eight notifications across an order's life — placed, contract sent, contract signed, paid, fulfilled, and three rental reminders:

Connections are the interesting half. A single VPS holding ten thousand idle SSE streams is ordinary — what I flagged earlier was an nginx default, not a hardware ceiling. The budget per stream, end to end:

kernel socket, client side ~10 KB → 100 MB kernel socket, nginx↔node ~10 KB → 100 MB nginx connection state ~2 KB → 20 MB Node socket + HTTP response ~20 KB → 200 MB Hono stream + hub closure ~10 KB → 100 MB ─────── ─────── ~52 KB ~520 MB CPU: 10,000 × one 20-byte write per 25 s = 400 writes/sec ← noise file descriptors: 2 per stream on nginx, 1 on node = 30,000 Postgres connections used by SSE: 0 (the listener is 1, process-wide)

The Node line is the one I would measure rather than trust; the rest are well-established. Note the last row — the resource people expect to exhaust is the one SSE never touches. A stream holds a socket, not a database connection.

Scaling out is free, and that is a consequence of ADR-N2

Run the API under pm2 cluster mode and every worker independently LISTENs. Postgres delivers each notification to all of them; each fans out to its own subscriber map. Sessions live in the database, so no sticky routing is needed, and the sweep running three times is already safe because of the dedupe key.

flowchart LR PG[("NOTIFY")] --> W1["worker1"] PG --> W2["worker2"] PG --> W3["worker3"]

Each proxied stream is two connections, client-side and upstream. nginx worker_connections defaults to 512–768 per worker, so you stop accepting somewhere around a thousand streams with no error that points at nginx. A 1024 soft ulimit on the Node process gives out at roughly the same place. Both are in the checklist near the end of this plan.

The target is 10,000 concurrent users, and that is not 10,000 per second

Settled: a holiday peak should hold ten thousand people with the site open at once. The full tuning list applies, cluster mode included. But the second half of that target — “so it should process 10k per second” — is a different quantity, and treating the two as the same number is what would make this plan look impossible.

Concurrent users and notifications per second are decoupled here, because a notification is produced by an order, not by somebody looking at a page. Ten thousand people browsing the catalogue produce zero notifications between them. What those ten thousand connections cost is one heartbeat each per 25 seconds:

10,000 concurrent visitors → SSE heartbeat 10,000 ÷ 25 s = 400 writes/sec ← trivial → catalogue browsing Astro SSR's problem, not this pipeline's Say 3% of them order within the same minute — a very good day: → 300 orders/min = 5 orders/sec → ~2 notifications each at placement time = 10 NOTIFY/sec NotifyQueueLock starts to matter at 5,000 NOTIFY/sec So: about 0.2% of the ceiling, at the busiest minute of the year.

For 10,000 notifications per second you would need roughly 1,250 orders per second sustained — about 108 million orders a day. Amazon's worldwide Prime Day peak is in the region of 4,000–5,000 orders per second. That number is not a forecast of this business; it is the concurrent-user figure carried across into the wrong unit.

Sustained throughput above roughly 5,000 NOTIFY/sec — around 600 orders per second. At that point pg_notify stops being the right fan-out and the answer is Redis pub/sub or NATS carrying the envelope, with the outbox table unchanged behind it. It is a swap of hub.ts, not a redesign, because everything else already treats the table as the truth. Worth knowing the threshold exists; you are three orders of magnitude below it.

So the work the 10k answer buys is entirely on the connection side — cluster mode, the file descriptor and sysctl list, hidden-tab disconnect and the shared heartbeat timer. None of it is database work.

Two changes cut the connection count before any tuning, and I would do both regardless. A stream whose tab has been hidden for five minutes is holding 52 KB to do nothing, so it should close on visibilitychange and reopen on focus at the cost of one snapshot fetch — in any real deployment most “concurrent” connections are abandoned tabs, so this alone is likely a three- to five-fold reduction. And the heartbeat belongs on one shared interval walking the hub map, not on stream.sleep() inside each connection's loop, which would mean ten thousand pending timers and ten thousand pending promises to save a single setInterval.

Payment status does not notify anybody, because nothing automatic moves it

An earlier draft of this plan asked which payment transitions should reach the customer. That question had a bad premise and has been dropped. An order does carry two independent statuses — status and paymentStatus — and they do move independently, which is correct: a bank transfer clearing days after the goods went out is a real sequence. But paymentStatus is only ever moved by service.transition, called from the admin routes by a person. modules/payments is reporting and CSV export; there is no gateway and no webhook anywhere in the repo.

So “the payment failed” is not an event the system discovers — it is an operator typing what they already know, with the customer usually on the phone at the time. A notification saying it back to them adds nothing. order.payment_changed is removed from the catalogue above. When Nexi XPay lands and a webhook starts moving that column on its own, the question becomes real and worth reopening — the row shape needs no change to accommodate it.

Rental reminders: feed and email, with the email switchable off

Decided. They are the only notifications in the set with a deadline attached, which is what argues for email; they are also the only ones that recur on a schedule, which is what makes them the ones people ask to switch off. One new preference on the account covers it.

Transactional mail is not part of that preference and is not listed in the UI at all — order confirmations, activation links and password resets stay unconditional. The preference governs rental.ending_soon and order.upcoming, which are the two the customer could reasonably call a nuisance.

Customer and admin notifications differ in who they point at and in nothing else. Two tables would duplicate the hub, the route shape, the sweep and the read-state column in order to express that one difference.

CREATE TYPE notification_audience AS ENUM ('customer', 'admin'); CREATE TABLE notifications ( id uuid PRIMARY KEY DEFAULT gen_random_uuid(), audience notification_audience NOT NULL, customer_account_id uuid REFERENCES customer_accounts(id) ON DELETE CASCADE, admin_user_id uuid REFERENCES admin_users(id) ON DELETE CASCADE, type text NOT NULL, -- 'order.status_changed' data jsonb NOT NULL, -- typed union, English keys order_id uuid REFERENCES orders(id) ON DELETE CASCADE, dedupe_key text, -- set by the sweep, never by an event read_at timestamptz, created_at timestamptz NOT NULL DEFAULT now(), CONSTRAINT notifications_recipient_check CHECK ( (audience = 'customer' AND customer_account_id IS NOT NULL AND admin_user_id IS NULL) OR (audience = 'admin' AND admin_user_id IS NOT NULL AND customer_account_id IS NULL) ) ); -- Named explicitly. Byte counts against Postgres's 63-byte identifier limit: CREATE INDEX notifications_customer_feed_idx ON notifications (customer_account_id, created_at DESC); -- 31 CREATE INDEX notifications_admin_feed_idx ON notifications (admin_user_id, created_at DESC); -- 28 CREATE UNIQUE INDEX notifications_dedupe_key ON notifications (dedupe_key) WHERE dedupe_key IS NOT NULL; -- 24

The CHECK follows orders_customer_link_check: two columns that must agree are made unable to disagree in the database rather than in a service. Drizzle's derived foreign-key names here come to 57 and 45 bytes, so only the indexes strictly need naming — they are named anyway, because a name that fits by luck is a name that breaks on the next column rename.

An admin notification goes to every admin holding the relevant permission code from @mia/permissions, as one row each. That is N inserts where N is the size of the operations team — currently a handful. A shared row plus a notification_reads join table would buy nothing at that size and would leave two mechanisms answering “have I read this”. It is the one decision here that is clearly wrong at fifty thousand recipients and clearly right at five.

What emit() looks like

export async function emit(tx: Database, n: NotificationInput) { const [row] = await tx.insert(notifications) .values(n) // The sweep passes a dedupeKey; event-driven callers pass none. .onConflictDoNothing({ target: notifications.dedupeKey }) .returning({ id: notifications.id }); // Nothing was inserted — a repeated sweep tick. Say nothing. if (!row) return; const envelope = JSON.stringify({ id: row.id, type: n.type, audience: n.audience, recipientId: n.customerAccountId ?? n.adminUserId, }); // Queued by Postgres, delivered to listeners at COMMIT — or dropped with // everything else if this transaction rolls back. await tx.execute(sql`select pg_notify('notif', ${envelope})`); }

NOTIFY payloads are capped at 8000 bytes and the error is raised at commit — a fat payload would turn a notification into a failed order transition. Four short fields can never approach the cap. The hub reads the row itself, and only when somebody is listening for it.

The one existing call site changes by a single line. applyTransition already opens a transaction to keep the status column and its order_status_events row from coming apart; the notification joins that same invariant.

export async function applyTransition(db: Database, event: StatusEventData) { await db.transaction(async (tx) => { await tx.update(orders).set({ [event.field]: event.toValue }) .where(eq(orders.id, event.orderId)); await tx.insert(orderStatusEvents).values(event); + await notifications.emitOrderTransition(tx, event); }); }

One process-wide listener, one in-memory map from recipient to open streams, and a row read that only happens when that map has an entry for the recipient.

flowchart LR K["COMMIT"] -->|envelope| L["LISTEN"] L -->|onNotify| H["hub.ts"] H -->|watched| DB[("notifications")] H --> T1["tab1"] H --> T2["tab2"]

LISTEN has no backlog. A payload sent while no process is listening is simply gone. That is tolerable only because the row is already committed and the next snapshot fetch returns it — which is why the snapshot is mandatory rather than an optimisation, and why the stream is described everywhere in this plan as a hint.

sequenceDiagram participant B as Browser participant H as Hub / LISTEN participant D as notifications B->>D: GET /notifications (snapshot) D->>H: NOTIFY one H->>B: event notification Note over H: LISTEN connection drops D--xH: NOTIFY two, lost D--xH: NOTIFY three, lost Note over H: postgres.js reconnects, onlisten fires H->>B: event resync B->>D: GET /notifications D->>B: one, two, three Note over B: feed correct

The obvious alternative is a monotonic bigserial and WHERE seq > :lastSeen on reconnect, driven by SSE's own Last-Event-ID. It has a hole: a sequence number is taken when the INSERT runs, but the row becomes visible at COMMIT, and commits do not finish in sequence order. A transaction holding 41 can commit after one holding 42, and a client that has already advanced past 42 never sees 41 again. Re-reading the newest page has no such hole and costs one indexed query per reconnect per customer.

const streams = new Map<string, Set<SSEStreamingApi>>(); export function start(sql: Sql) { return sql.listen('notif', async (payload) => { const env = parseEnvelope(payload); const open = streams.get(env.recipientId); if (!open?.size) return; // nobody watching: no query, no work const row = await repo.findById(db, env.id); for (const s of open) await push(s, 'notification', row); }, () => broadcastAll('resync', {}), // first LISTEN and every reconnect ); }

The route itself is behind requireCustomer and sets two headers. The heartbeat is doing two jobs at once: it keeps nginx's 60-second proxy_read_timeout and Cloudflare's roughly 100-second idle timeout from closing an idle stream, and it is the only way the server ever learns that a closed tab is gone — with no traffic, a dead socket looks exactly like a quiet one.

docs/nginx/miamedical_prod.conf leaves proxy_buffering on and proxy_read_timeout at the default. X-Accel-Buffering: no settles the first per response; the 25-second heartbeat settles the second. Both are properties of the response, so dev and prod behave identically without touching a vhost. The tuning in the checklist below is about scale, not about making it work.

“Three days left” is not an event. Nothing writes it and nothing commits it — it becomes true while the process is idle. It needs a clock, and a clock needs a way to not repeat itself.

const THRESHOLDS = [7, 3, 1] as const; // days before rental_end_date async function run(db: Database) { for (const days of THRESHOLDS) { const due = await repo.rentalsEndingIn(db, days); // Europe/Rome calendar days for (const r of due) { await db.transaction((tx) => emit(tx, { audience: 'customer', customerAccountId: r.customerAccountId, type: 'rental.ending_soon', orderId: r.orderId, data: { orderNumber: r.orderNumber, endsOn: r.endsOn, daysLeft: days }, dedupeKey: `rental.ending_soon:${r.orderId}:${days}d`, })); } } } // Hourly, unref'd, and run once at boot. All three are safe because the unique // index on dedupe_key makes a repeat a no-op rather than a duplicate. setInterval(() => void run(db), 3_600_000).unref();
  • A restart does not re-notify — the key exists, the insert does nothing, and emit returns before it reaches pg_notify.
  • Two or three API workers are safe. They race on the unique index and all but one lose. No advisory lock, no leader election.
  • Bucketing is by calendar day in Europe/Rome, not by 72 hours — a customer told “3 days left” on a rental ending Friday means Tuesday, whatever time the tick fired.

  • The storefront resolves the customer's locale from the URL, which is how every other localized string on the site is chosen.
    •

    Because the feed renders client-side from type plus data, the server needs no language handling at all for it — unlike the admin's product lists, which send ?locale= so the server can collapse a translated field before it goes out. One rule keeps it that way, and it is worth stating because breaking it is easy and silent:

    orderNumber, a date, a count — never a product title. A translated string written into data freezes that row into one language forever, which is the exact failure ADR-N4 exists to prevent. Anything localized is referenced by id and resolved at render.

    The admin chrome is not translated yet — ui-lang was built for it and the work has not happened. So an operator who switches to English gets an English notification feed inside a panel whose buttons have not moved. That is the intended direction of travel rather than a defect, but it will look odd for a while and is better expected than discovered.

    Email is the part this does not reach for free

    The feed is cheap because it renders in a browser that knows its language. Email is rendered on the server, into a message sent once, and packages/templates is Italian-only — every customer message hardcodes Italian copy. So with no further work, a German customer would read a German feed and receive an Italian reminder email.

    Two things are missing, and neither is large on its own. customer_accounts has no language column, so nothing records which language a customer reads — it would be captured at checkout from the storefront locale, which is already known at that moment. And the templates need per-language copy. There is a good precedent for the second: literal/contract/language.ts defines ContractLanguage as deliberately narrower than LanguageCode, precisely so that registering a new site language cannot silently claim a translated document exists. A NotificationEmailLanguage union following that pattern widens only when the copy has actually been written.

    In scope, as phase three: a language on the account

    Decided, and with a design: the account carries the language, it is set when the account is created, the customer can change it afterwards, and anything we cannot place falls back to English. Since an account only ever comes into existence through checkout — there is no signup form and there will not be one — the moment of creation is the moment the storefront locale is known, which is what makes capturing it free.

    ALTER TABLE customer_accounts ADD COLUMN language language_code NOT NULL DEFAULT 'en';

    It reuses the existing language_code pgEnum rather than introducing a second list. packages/validators/src/language.ts is explicit that nothing anywhere may hardcode a language code or count them, so a fifth language reaching this feature is the documented adding-a-language.md procedure and nothing else.

    MomentWhere the language comes from
    Account created by checkoutThe storefront locale in the URL. Always one of the four, so the fallback never fires here.
    Customer changes itA control in the account area, phase two. Labelled as the language we write to them in.
    Operator changes itThe customer detail screen in the admin — an operator on the phone with a tourist should be able to fix this without asking them to log in.
    Anything elseen. An order raised through the admin, a future integration, a row that predates the column.

    Existing accounts cannot have their language recovered: orders records no locale, so there is nothing to read it from. Every one of them has been emailed in Italian since the system started. Defaulting them to English would silently switch the language of every existing customer's mail the day phase three ships — a regression dressed as a default.

    So the migration backfills existing rows to it and leaves the column default at en for new unknowns. Your rule applies exactly where you meant it — a language we cannot place — and not to a population whose language we can infer from the fact that we have been writing to them in it for a year. If you would rather they all move to English, it is one UPDATE, and better run deliberately than as a side effect.

    The stored language governs what we send, not what they are looking at

    A deliberate boundary. The storefront's own language stays URL-driven, as it is today: that is an SEO commitment governed by routes.ts, and a stored preference that redirected people away from the URL they asked for would fight it. So the feed renders in the language of the page being read, and email renders in the language stored on the account.

    That is coherent rather than a compromise: the feed is something you are looking at, and email is somewhere we reach you when you are not. Labelling the account control “the language we write to you in” rather than “your language” is what keeps it from reading as a bug.

    What phase three actually contains

  • The column above, its migration, and the backfill to it.
  • Capture at checkout — the storefront already knows its locale; this passes it on the order payload and resolveForOrder writes it.
  • The control in the account area, and the same field on the admin's customer screen.
  • Per-language copy for the customer templates. This is the bulk of it, and it is writing and reviewing copy rather than code — four languages across the reminder messages first, then the four existing order and auth messages so that no Italian-only message is left behind.
  • A NotificationEmailLanguage union following literal/contract/language.ts, so registering a fifth site language cannot silently claim a translated email exists. Until a language is in that union, a customer holding it receives English.
    •

    Until phase three lands, every email stays Italian exactly as it is now. Nothing about phases one and two depends on it, and the feed is multilingual from the day phase one ships.

  • No web push, no service worker. A closed tab gets email or nothing. Push needs a VAPID key pair, a subscription table and an unsubscribe story — a separate project, and one that only pays off once the feed has shown which events people actually care about.
  • No grouping or digest. An order that moves three times in an afternoon produces three rows. Collapsing them is a read-side concern and lands later without a migration.
  • No retention. Nothing deletes a read notification. The existing expired-session sweep is where that belongs once the table is big enough to notice.
  • No retries and no dead-letter. Deliberate: the table is the record, so there is nothing to retry. Revisit only if the requirement becomes “push it even though the API was down”.
  • Thresholds are constants. T−7/T−3/T−1 lives in code. platform_settings is a key→jsonb bag and costs an INSERT, so moving them is cheap — no operator has asked.
  • No delivery receipt. The feed records that a notification exists, not that a human saw it. read_at is the closest thing, and a customer who never opens the tab leaves it null forever.
