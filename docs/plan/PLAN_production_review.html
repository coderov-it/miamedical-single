In plain terms: the date filter

An index on placed_at is a sorted list of timestamps. To use it, the database needs a start and an end on that list. Today's filter first turns every timestamp into a date, then compares the dates. The conversion also uses the database's day, which is UTC by default, not the Rome day the operator picked.

In plain terms: the search box

A normal index is sorted from the first character, like a phone book. A search for %1042% can match anywhere inside the value, so the phone book doesn't help, and every row is read and compared. A trigram index stores every three-character piece of each value. Then the database can look up the pieces of the search term instead.

Normal index (today) Trigram index (pg_trgm) 1. stored as MIA-2026-000001, MIA-2026-000002, … "mia" "202" "026" "001" "010" "104" "042" … 2. "%1042%" can start anywhere → no jump pieces "104" + "042" → rows holding both 3. rows compared every order, on every keystroke only those candidates 4. fallback: "10" every order still every order (no 3-character piece)

In plain terms

A rental's dates have no columns of their own. They live as text inside the JSON snapshot of each order line:

{ "pricingMode": "rental", "rental": { "startDate": "2026-10-01", "endDate": "2026-10-08", "duration": 7, "unit": "day" } }

To answer "which rentals are overdue?", the database has to open that JSON on every order line and turn the text into a date. Only then can it compare and sort. No index can help, because there is no column to index. Then, for each row it keeps, it looks up the newest contract twice: once for its id and once for its status.

Today Proposed 1. find overdue open JSON on all 10,000 lines, rental_end_date column + partial index text → date, compare with today order_items_rental_end_idx → jump to overdue lines 2. sort by end date sort what step 1 produced already in index order 3. newest contract 30 rows × 2 lookups (id, then status) 30 rows × 1 lookup (LATERAL join returns both), = 60 lookups served by contracts_order_live_created_idx 4. hourly sweep repeats step 1 for: ending soon, starting same column, same index, every pass soon, extend offer

The new column has to stay equal to the JSON, so both are written in the same transaction:

1. checkout places the order JSON endDate 2026-10-08 rental_end_date 2026-10-08 (one transaction) 2. renewal contract is signed JSON endDate 2026-10-15 rental_end_date 2026-10-15 (one transaction) 3. step 2 fails halfway both roll back → both still say 2026-10-08

Why not just index the JSON expression? PostgreSQL only indexes expressions whose result can never change. Turning text into a date depends on the session's date-format setting, so PostgreSQL refuses to index it. A real date column avoids that.
